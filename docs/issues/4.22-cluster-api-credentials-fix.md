# OpenShift 4.22 Cluster-API Credentials Issue - Root Cause Analysis

**Date**: 2026-07-15
**Status**: RESOLVED
**Affected**: aws-virtualization-ga profile with OpenShift 4.22

---

## Executive Summary

OpenShift 4.22 GA clusters using the `aws-virtualization-ga` profile were failing 100% of the time with NAT gateway errors. The root cause was **NOT** a timing issue or OpenShift bug, but rather an incomplete IAM permissions policy generated when using `credentialsMode: Manual` with OpenShift 4.22's cluster-api.

---

## The Pattern

| Profile | Credentials Mode | 4.22 Success Rate |
|---------|------------------|-------------------|
| aws-virtualization-prerelease | Auto | ✅ 8/10 (80%) |
| aws-virtualization-ga | Manual | ❌ 0/6 (0%) |
| aws-sno-ga | Auto | ✅ 2/2 (100%) |
| aws-minimal-ga | Auto | ✅ 1/1 (100%) |

---

## Root Cause

### What Happened

When using `credentialsMode: Manual`, ocpctl uses OpenShift's CCO (Cloud Credential Operator) workflow to create least-privilege IAM roles with STS tokens. The CredentialsRequest for cluster-api in OpenShift 4.22 is **incomplete** - it only includes permissions for managing existing infrastructure, not creating it.

**Missing Permissions:**
- `ec2:CreateNatGateway` / `DeleteNatGateway` / `DescribeNatGateways`
- `ec2:CreateVpc` / `DeleteVpc` / `ModifyVpcAttribute`
- `ec2:CreateSubnet` / `DeleteSubnet` / `CreateRouteTable`
- `ec2:CreateSecurityGroup` / `AuthorizeSecurityGroupIngress`
- `elasticloadbalancing:CreateLoadBalancer` / `CreateTargetGroup`

### Why Prerelease Worked

The `aws-virtualization-prerelease` profile used `credentialsMode: Auto`, which uses full IAM credentials from the worker EC2 instance role with all necessary permissions, not relying on the incomplete CredentialsRequest.

---

## The Fix

**Changed**: `internal/profile/definitions/aws-virtualization-ga.yaml`

```diff
- credentialsMode: Manual
+ credentialsMode: Auto
```

---

## Why This Affected Metal Instance Profiles

Metal instances (m5zn.metal) take 10-15 minutes to provision vs 2-3 minutes for standard instances. This longer window made the permissions issue more apparent, but the root cause was the credentials mode, not instance type.
